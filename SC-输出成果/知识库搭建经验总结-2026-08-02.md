# 一消知识库搭建经验总结（供注安复用）

> 生成日期。2026-08-02
> 用途。用户下次搭建注册安全工程师（注安）知识库时，参照本总结避免重复踩坑。
> 本文档记录一消知识库搭建全过程的成功经验、失败教训、关键技术方案。

---

## 一、总体流程（本次采用的步骤）

1. **规划**。先写实施计划（含目录结构、元数据规范、特殊资料处理方案）
2. **建骨架**。CLAUDE.md 人设+规则、知识库目录、条目模板、错题模板
3. **收资料**。用户投喂 PDF（讲义/习题/真题/思维导图/奇门遁甲/错题本）
4. **处理 PDF**。文字版直接提取，图片版 OCR
5. **建知识条目**。按模块打标，标注来源页码
6. **录入错题**。按知识点聚合，生成薄弱分析
7. **输出成果**。易错点对比、知识汇总，存 SC-输出成果/
8. **备份**。GitHub 私有仓库 + LFS

---

## 二、关键决策（对注安同样适用）

### 1. 纯文件式知识库，不用数据库
- 所有资料天然是文档（PDF/讲义），Markdown + YAML frontmatter 足够
- 零依赖，随开随用，git 可版本管理
- **注安同样适用**，无需引入数据库

### 2. 元数据打标（核心）
- 每个知识条目 YAML frontmatter 含：module、sub_module、tags、weight、regulation_refs、related
- **来源页码必须标注**。奇门总结 P38、教材3号书 P104 等
- **教训**。来源页码标注口径要统一。奇门页码 ≠ 教材页码，用户明确要求教材页码

### 3. CLAUDE.md 规则先行
- 人设、回答协议、奇门遁甲溯源规则、错题运营、知识库依据规则、输出归档
- **所有提问通用"知识库依据规则"**——回答必须以知识库为准，找不到标存疑不猜
- **经验**。规则要一次写全，避免后期反复补（本次补了2次规则：笔记校验→通用提问、输出归档）

### 4. 输出成果归档
- 所有输出型成果存 `SC-输出成果/`，文件名 `主题-日期.md`
- 用户原始输入（笔记原文）存 `notes/`，与输出分开

## 三、PDF 处理（本次最大的坑）

### 3.1 先检测文字层，别急着 OCR
- **判断方法**。`pdftotext` 提取测试。有文字 → 直接提取；无文字（乱码/空）→ 图片版，需 OCR
- **本次结果**。22 个 PDF 中 14 个有文字层直接提取，8 个图片版需 OCR（2136 页）
- **教训**。所有 PDF 先统一检测文字层，避免对可提取的文件白做 OCR

### 3.2 中文 PDF 的文字层陷阱
- pdftotext 对 GBK 编码 PDF 报 `Couldn't find 'GBK-EUC-H' CMap` 乱码
- **解决**。用 Node + pdfjs-dist 提取，利用内嵌 ToUnicode 映射，可正确读中文
- **工具**。tools/extract.js（pdfjs-dist 提取，按行聚合）

### 3.3 OCR 工具链（图片版 PDF）
- 需要三件套。tesseract + poppler(pdftoppm) + 中文语言包 chi_sim.traineddata
- **安装坑**。
  - tesseract 用 winget 装（UB-Mannheim.TesseractOCR），需 `--source winget` 指定源
  - chi_sim.traineddata 从 raw.githubusercontent.com 下载（github.com 直连不稳）
  - pdftoppm 用 winget 装 oschwartz10612.Poppler，但**不在 PATH**，需完整路径
- **tesseract 5.4 不能直接读 PDF**，必须 pdftoppm 先转 PNG

### 3.4 OCR 并行加速（最重要提速）
- **单进程 6.6 页/分钟 → 24核并行 80 页/分钟（12倍）**
- 方案。逐页任务并行，每页"转换+OCR"独立，用 bash `&` 后台作业控制并发数
- **CPU 24核**，并发开到 16-24 都可行；32GB 内存无压力
- **坑**。pdftoppm 单页输出文件名是 `p-NNN-NNN.png` 而非 `p-NNN-001.png`，脚本写死导致空页——**必须动态匹配实际 PNG 文件名**
- **坑**。shell 后台任务 + Claude 后台管理有时序问题，合并阶段可能丢页/重复页——**用 node 脚本重新合并最稳**

### 3.5 OCR 质量差异（重要教训）
- **文字版 PDF 提取质量远高于图片版 OCR**
- 图片版 OCR 对**密集表格**识别差（行列错位、字被拆），对纯文字页尚可
- **奇门遁甲总结.pdf 是文字版** → 质量高，成为知识库主要来源
- **奇门遁甲横/竖版是图片版** → OCR 乱码多，口诀拆分被迫放弃
- **教训**。资料来源优先用文字版；图片版只作补充，不当作权威来源

## 四、知识库建设经验

### 4.1 条目建设顺序
- 按**错题高频优先**建条目（水系统、火灾危险性、耐火等级、安全疏散最先建）
- 后补低频模块（装修、平面布置、安全管理、法规）

### 4.2 知识库盲区（教训）
- 建条目时**聚焦了高频考点，漏了部分内容**
- 实例。应急照明条目漏了"民用建筑电气照明回路电流"规则，导致笔记校验漏判
- **教训**。校验前先排查知识库盲区；用户求证后及时补条目（本次补了电影院剧礼、水箱支架等）

### 4.3 校验流程（迭代验证）
- 笔记校验发现知识库错误，靠**用户求证**纠正
- 本次用户求证纠正了我3处误判（电影院剧礼楼板、管道井甲级门、疏散密度）
- **教训**。知识库判定不能机械，遇到不确定的标"存疑"并标注，让用户定夺

### 4.4 口诀拆分
- 按模块分组（10个文件75条）优于每句一文件
- **教训**。横竖版 OCR 质量差，自动提取噪声大，用户决定放弃拆分——**先评估来源质量再决定拆分范围**

## 五、技术环境备忘

### 5.1 本机可用工具
| 工具 | 状态 | 用途 |
|---|---|---|
| git 2.55 | ✅ | 版本管理 |
| git-lfs 3.7.1 | ✅ | 大文件（PDF） |
| gh CLI 2.97 | ✅ 完整路径 `C:/Program Files/GitHub CLI/gh.exe` | GitHub 操作 |
| tesseract 5.4 | ✅ `C:/Program Files/Tesseract-OCR/` | OCR |
| poppler | ✅ winget包，完整路径 | PDF转图 |
| Node 24 + pdfjs-dist | ✅ tools/node_modules | PDF文字提取 |
| 代理 | ✅ 127.0.0.1:7890 | 访问 GitHub |

### 5.2 代理配置（访问 GitHub 必须）
```bash
# git 代理
git config http.proxy "http://127.0.0.1:7890"
git config https.proxy "http://127.0.0.1:7890"
# gh 环境变量
export HTTPS_PROXY="http://127.0.0.1:7890"
export HTTP_PROXY="http://127.0.0.1:7890"
```
- **教训**。curl/浏览器能通 GitHub 但 gh 可能连不上（DNS 返回不同 IP），走代理最稳
- gh 登录用 PAT（`gh auth login --with-token`），交互式登录在 Git Bash 无 TTY 会卡死

### 5.3 GitHub 备份
- 私有仓库 + LFS 管理 PDF（>100MB 文件必须 LFS）
- 免费版 LFS 配额。1GB 存储 + 每月1GB流量（本次1.9GB 略超但推送成功）
- 建仓用 REST API（`POST /user/repos`），gh 的 GraphQL 建仓可能报权限错（bug）
- token 需要 `repo` 权限；删除仓库 token 可能无权

## 六、注安搭建差异化建议

### 6.1 注安与一消的不同
| 维度 | 一消 | 注安 |
|---|---|---|
| 科目 | 实务/综合/案例（偏技术规范） | 法规/管理/技术基础/专业实务 |
| 核心 | 数值规范记忆（防火间距、耐火等级） | 法规条款、安全管理、专业实务 |
| 记忆点 | 数字、口诀、规范条文 | 法条、管理制度、事故案例 |

### 6.2 注安知识库应侧重
- **法规条款库**。安全生产法、各专业法规（相比一消，法规占比更高）
- **管理制度**。安全生产责任制、隐患排查、应急管理
- **专业实务**。按专业方向分（煤矿/化工/建筑施工等）
- 事故案例分析（一消几乎没有，注安是重点）

### 6.3 复用建议
- 直接复用。目录结构、CLAUDE.md 规则框架、错题聚合模式、SC-输出成果归档
- 需调整。模块划分（一消按建筑防火/消防设施，注安按法规/管理/技术/实务）、口诀来源处理
- 元数据标签维度。一消用 module/tags；注安建议加"专业方向"维度

## 七、本次最大教训清单（按影响排序）

1. **OCR 前先检测文字层**。图片版和文字版处理方式完全不同，先判断省大量时间
2. **并行是 OCR 提速关键**。单进程 vs 24核并行，12倍差距
3. **来源页码口径统一**。奇门页码 vs 教材页码要分清，用户明确要教材页码
4. **知识库要防盲区**。高频考点覆盖后，校验暴露盲区，及时补
5. **校验允许用户求证**。知识库判定不是最终答案，存疑项交给用户
6. **输出成果统一归档**。SC-输出成果/ 文件夹，避免散落
7. **GitHub 走代理 + LFS**。大文件必须 LFS，访问必须代理
